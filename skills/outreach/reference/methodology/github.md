# GitHub

取数见 [../datalayer/public.md](../datalayer/public.md)。
**唯一一个不用第二跳就能拿到邮箱的渠道** —— 前提是本人把它设为公开。

## 入口

**搜索型**,而且是这批渠道里发现能力最好的:按用户、按仓库、按代码三种搜法,结果稳定。

从「主题 → 人」有两条路:

- **搜仓库再取作者** —— 按 topic / 语言 / star 数筛项目,再看谁在维护。
  质量高于直接搜用户。
- **搜用户** —— 匹配 bio 与用户名。同别处一样,容易命中名字里带关键词的空壳号。

## 拿联系方式

1. **用户资源的 `email` 字段** —— 本人设为公开时直接可用。**这是主路。**
2. **`blog` 字段** —— 个人站,第二跳的起点,
   见 [landing-page-two-hop.md](landing-page-two-hop.md)。
3. **`bio` / `company` / `twitter_username`** —— 补充身份判断,也可能带联系线索。
4. **组织的 README 或 `.github` 仓库** —— 项目类目标的对外入口常写在这里。

## 一条必须守的线:不从 commit 里挖邮箱

commit 的 author email 在公开数据里是拿得到的,而且命中率远高于资料页的 `email` 字段。

**不用它。** 那是提交元数据,不是这个人**表示愿意接收联系**的地址;GitHub 自己为此提供了
`noreply` 转发地址,正说明多数人不希望它被当作联系方式。用它做 outreach 会踩到
本项目安全规则里「公开的商务联系」这条界线。

只用资料页公开的 `email` 字段——那是本人主动设为公开的。

## 项目 vs 个人

目标表里 GitHub 这一档混着两类,contact note 已经区分过:

- **个人维护者** —— 资料页邮箱或个人站,算数。
- **项目/组织** —— 多数明确写着「走 issue / discussion / Discord,不接受 cold email」。
  这类的联系方式形态应当记成对应的入口 URL,**不是邮箱**。

硬拿一个 `contact@` 去发信,对开源项目是最容易被拉黑的做法。

## 停止语义

搜索型——**连续无新**。取数层的分页上限是硬边界,但翻到它**不等于**目录型的「翻到底」:
那只说明这次查询问完了,换个查询词还有人。仍然记作连续无新,别混。

## 去重的键

`(用户名或组织名, GitHub)`。

GitHub 的 handle 唯一且稳定,是这批渠道里判重前提最扎实的一个。

## 边界

- **不挖 commit 邮箱**(上面那条)。
- 项目类目标拿不到人是常态,不是失败。

## 待验证

- 资料页 `email` 字段在目标表现有的 28 行 GitHub 上的实际公开率。经验上不高,
  但这一档本来就有一半是项目而非个人。
- 「搜仓库再取作者」与「搜用户」的质量差距。
- 组织类目标的对外入口(issue / discussion / Discord / `contact@`)记成哪种
  `Contact Method` 值——现有的下拉选项里没有完全对应的。
