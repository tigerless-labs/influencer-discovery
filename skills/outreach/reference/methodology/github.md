# GitHub

取数见 [../../../../datalayer/public.md](../../../../datalayer/public.md)。
**唯一一个不用第二跳就能拿到邮箱的渠道** —— 前提是本人把它设为公开。

## 入口

**搜索型**,而且是这批渠道里发现能力最好的。从「主题 → 人」有三条路,实测差距明显:

- **搜仓库再取作者** —— 按 topic / star 数筛项目,再看谁在维护。**这是主路**:
  邮箱公开率、外链填写率、粉丝量都最高,粉丝中位数比搜用户高一个量级,没有空壳号。
  代价是 owner 里三分之二是组织,要先按类型丢掉。
- **热门仓库的高频贡献者** —— **唯一不花搜索配额的发现方式**(走的是普通接口),
  而且返回的全是个人账号,正好补掉上一条「要丢掉三分之二组织」的代价。质量仅次于主路。
- **搜用户** —— **查询词必须是短语,不能是单词。** 单词查询会匹配到登录名,
  出来一半是名字里带那个词、bio 与主题无关的人;短语查询这类噪声基本消失。

**不要走 issue 发起人这条路。** 全线垫底 —— 发 issue 的是*用户*不是*作者*,
与「有受众」负相关。

## 判「会写博客、有受众」

两个信号必须**同时**看,单用任何一个都会失手:

- **`blog` 指向的是不是内容站** —— 光看 URL 形态不行,多数人填的是裸域名。
  抓一次首页,**有 RSS 是最干净的单条判据**;跑在内容托管平台上、或首页有多条日期化链接
  也算。
- **粉丝量过线** —— 只看上一条会捞出一堆没人读的博客。

**bio 里说自己写作、把博客源码放 GitHub,和有人读,是两回事。** 这两类人群的内容站比例
最高,但粉丝中位数只有个位数到二十几,交叉后基本被筛掉。

## 拿联系方式

四条能直接产出邮箱的路,按净增量排。**并集实测过半,比只看资料页高近二十个百分点:**

1. **用户资源的 `email` 字段** —— 本人设为公开时直接可用。**这是主路**,公开率不低。
2. **profile README**(与用户名同名的那个仓库)—— **净增量最大的一条**。
   README 本身近半数人有,其中三分之一带邮箱,而且相当一部分人的资料页字段是空的。
3. **`blog` 字段的落点** —— 第二跳的起点,见
   [landing-page-two-hop.md](landing-page-two-hop.md)。走仓库那条路进来的人,这个字段过半有值。
4. **`<用户名>.github.io`** —— **独立的第二跳起点**,不依赖 `blog` 字段。
   有些人没填 `blog`,但这个站活着 —— 他们没有别的落地页可跳。

顺手项:**本人 star 最高那个仓库的 README** —— 反正要读它判身份,顺带扫一遍。
`CONTRIBUTING.md` 不值得多打一次。

**补身份、不补邮箱的:** 社交账号接口有一半人有值,但它的 twitter 就是资料页字段的镜像,
**零增量**;真正有用的是里面那类「其它网址」,少数人只在那里留了线索。
`company` 字段填的多是公司名,**对拿邮箱无用**,只当身份判据。

## 一条必须守的线:用途绑定的地址不算数

**不从 commit 元数据里挖邮箱。** commit 的 author email 拿得到,命中率也远高于资料页,
但那是提交元数据,不是这个人**表示愿意接收联系**的地址 —— GitHub 自己为此提供了
`noreply` 转发地址,正说明多数人不希望它被当作联系方式。

**`SECURITY.md` 里的地址同理不用。** 它确实常是本人的私人地址,但写在
「请把漏洞报到这里」的标题下 —— 用途是安全上报,拿它发 outreach 与拿 `abuse@` 发广告同性质。

这两条是同一条原则:**地址写在一个指定用途之下,就不构成「愿意接收商务联系」。**
只用本人主动设为公开的联系方式。

## 项目 vs 个人

- **个人维护者** —— 资料页邮箱或个人站,算数。
- **项目/组织** —— **这一档拿到的就不是人的地址**:组织资料页的邮箱填写率有一半,
  但前缀几乎全是 `hello` / `support` / `founders` / `info` / `contact` 这类角色地址。
  组织的对外入口应当记成 issue / discussion / Discord 的 URL,**不是邮箱**。

硬拿一个 `contact@` 去发信,对开源项目是最容易被拉黑的做法。

## 停止语义

搜索型——**连续无新**。取数层的分页上限是硬边界,但翻到它**不等于**目录型的「翻到底」:
那只说明这次查询问完了,换个查询词还有人。仍然记作连续无新,别混。

## 去重的键

`(用户名或组织名, GitHub)`。

GitHub 的 handle 唯一且稳定,是这批渠道里判重前提最扎实的一个。

## 边界

- **用途绑定的地址不用**(上面那条)。
- 项目类目标拿不到人是常态,不是失败。
- 赞助配置文件里**一个邮箱都没有**,它是平台 handle 表,是赞助入口来源、不是邮箱来源。
- **速率不止官方那两个数字。** 列仓库那类接口有独立的次级限流,**配额查询接口看不到它**,
  触发后要等整点配额重置,不是几十秒。**并发要压到很低**,否则流水线会整段哑掉。

## 待验证

- `blog` 落点只抓过首页,没跟 contact / about 页 —— 完整两跳的净增量会更高。
- 组织类目标的对外入口记成哪种 `Contact Method` 值 —— 现有的下拉选项里没有完全对应的。
