# 存储

## state 是 per-user 的,不是 per-repo 的

skill 从哪个目录触发都要能读到自己的判重库。放进 repo 就等于绑定了一个工作目录,
换个地方触发就会把见过的人当成新人重新发现一遍。所以流水线的持久状态全部住在用户级目录,
repo 里只剩代码、配置与合成 fixture。

## 三层,按两个正交判据分

**能不能重建**,与**人会不会打开**。

| | 重建 | 人看 | 住什么 |
|---|---|---|---|
| 凭据与本轮参数 | 不能 | 偶尔 | 密钥、目标表标识、本轮的三件事 |
| 索引与缓存 | **能** | 不会 | 判重库、走过的地址、抓取原文 |
| 成品 | 不能 | **会** | 运行报告 |

判重库进第二层的入场券是它可重建:合格的人在目标表里,能反过来播种。它是缓存,不是权威。

抓取原文也进第二层,但带一条额外约束:**只有解析器读它**。它是第三方文本,
读回任何拼 prompt 的路径就等于把未审查的内容当成自己的输入。这条靠读取口唯一来保证,
不靠纪律。

运行报告是唯一带着真人联系方式的人类可读文件。它不进 repo,也不该被转贴进任何对外产物。

## 记录的形状 —— core 与 payload

每个渠道原生给的字段完全不一样。塞进一张宽表的结果是稀疏表,且每加一个渠道就加一批列。

按**谁读它**切成两半:

- **core** —— 共享的后半段读的字段,从下游倒推、凑齐即止:判重要键,第二跳要自有站,
  闸门要受众与落点性质,写表要那几列。
- **payload** —— 渠道原生字段,原样存,**共享代码永不读**。只有该渠道的 adapter 认得它的形状。

加一个渠道等于加一个 adapter 加一种 payload,共享代码一行不动。反过来,
共享的后半段里一旦出现按渠道名分支的判断,这个划分就已经破了 —— 这是最好用的一条自检。

## 四条不变量

**判重的键就是主键。** 不另外发标识。键与判重依据一旦是两个东西,身份就有两种说法,
而误合并是那个永远看不见的错误方向。

**数字必须带单位。** 互动数、订阅数、粉丝数不是一回事。存值也存单位,
代码在跨渠道排序时就会被迫承认它们不可比,而不是默默比了。

**每个联系方式带来源。** 绑定用途写下的地址不构成愿意接商务联系。只存地址字符串,
这条规则以后就没法回溯执行;存了来源,规则随时能重跑。

**「没有」「没查」「失败」是三个状态。** 空值到底是查了他没填、还是压根没走这一跳,
决定重跑要不要重试。失败是第三种 —— 它不进判重库,只进报告,否则一次抖动就永久丢掉一个人。

## 记录一路加字段,不换类型

一个人在第几跳死掉都要留下一条完整记录,末尾带上他停在哪里。每个阶段换一个类型的话,
半路死掉的人无处安身,「log 记全部」就做不到。

## 分区跟着写入者走

一个渠道一个文件,因为写入方是一个进程。逻辑上它们是一张表,读的时候求并集 ——
判重要跨渠道读,走过的地址更是天然共享的。按读者切物理布局会坑住其余几种读法。

「最终可联系列表」是这张表上的一个视图,不是第四份存储。联系数据的权威是目标表。
