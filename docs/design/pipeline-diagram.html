爬过的都记下来，够得着的才进表

这个 skill 只负责三件事：打通数据层、记录规范、防重复， 其余都是读写操作。去重不靠解析链接，只靠一条规则—— 这个「人 + 平台」在 log 里出现过就跳过。 简单的那个，在真实数据上比复杂的那个准。

一个循环

使用者给的数是最终进表的合格行数，不是爬多少个。所以它是累积循环—— 但没有反馈，没有任何东西流回上游。

为什么不解析链接

看起来更聪明的那个方案，在真实数据上会删掉真人。

前提：log 里的「人」是机器从平台页抓的显示名，不是人手打的—— 这是它误合并为零的原因。哪天某个平台的显示名不稳定，这条假设就破，那个平台得单独处理。

四条不变量

  • 只追加，不修改目标表创建新行，永不改动任何已存在的格。人爱改哪列改哪列，不会冲突。
  • log 记全部，表只记合格的抓不到联系方式的人只进 log，表保持干净。
  • 失败不记 log超时、限流、网络错不算「爬过」——记了，一次抖动就永久丢掉一个目标。它们进运行报告。
  • 宁可不进表，不可编造联系方式抓不到就不进表，不猜一个。

定脉络，不定细节

设计只框住必须成立的，其余留到使用时——每轮意图不同，焊死等于让上一轮绑架下一轮。

设计定死

  • 三种停止原因可区分
  • 召回顺序跟随平台，不重排它给的结果
  • 产出率按渠道记录
  • 不做图遍历扩散

使用时才定

  • 要多少（合格行数）
  • 「符合要求」的门槛
  • 优先规模、贴合、成功率还是平台多样性
  • 先跑哪个平台、低产时换不换

怎么兜住

  • agent 的计划、实际、偏离、停止原因全进运行报告
  • 产出率是下轮估算的唯一依据——门槛变了数字就不可比
  • 约束靠记录，不靠预先规定
