# 设计文档索引

这个 skill 只负责三件事:**打通数据层、记录规范、防重复**。其余都是读写操作。

- [platforms.md](platforms.md) —— 打通:每个平台从哪进、怎么走、什么时候停。
- [records.md](records.md) —— 记录规范:log 记什么、表里写什么、报告记什么。
- [dedup.md](dedup.md) —— 防重复:一条规则,一个前提。

## 这里不写渠道做法

具体到某个平台的联系方式在哪一页、从哪个入口进、页面长什么样,归 `skills/outreach/`——
那是运维手册,会随平台改版而变。这里只写不随平台变的东西:两类形态、停止语义、两跳、取数规矩。

分界线是**变化频率**:平台一次改版就要改的,不该住在讲理由的文档里。

## 流程

使用者给一个数,指的是**最终合格的行数**,不是爬多少个。

```
循环 {
  发现一批候选        agent 自己规划顺序
  查 log,见过的跳过
  抓联系方式          平台页 → 本人站点
  记 log             不管抓没抓到都记
  合格的进目标表       有联系方式 且 符合要求
}
```

累积循环,没有反馈——没有任何东西流回上游。

## 不变量

- **只追加,不修改。** 目标表创建新行,永不改动任何已存在的格。
- **log 记全部,表只记合格的。** 抓不到联系方式的人只进 log。
- **失败不记 log。** 超时、限流、网络错不算「爬过」——记了,一次抖动就永久丢掉一个目标。
- **宁可不进表,不可编造。** 联系方式抓不到就不进表,不猜一个。

## 范围

止于拿到联系方式。发信、分层、成交跟踪、点击结算都在外面。

要多少、优先什么、「符合要求」的门槛、先跑哪个平台——**使用时再定**,不写进配置。
每轮意图不同,焊死等于让上一轮绑架下一轮。设计只保证这些决定留得下痕迹。
