触达流水线：一条撞上人的产线

八个阶段把目标从各渠道抓进来、去重、分层、定状态,然后写进一张 Google Sheet—— 写到那里就停。Sheet 上另有一半列属于人,流水线只读不写;人在那边的每一次编辑被读回来, 转成事件,喂回状态阶段。回路因此闭合。

完整流水线

机器侧是一条直线,真正的结构在右端:Sheet 是一道膜,两侧的列归属不同,谁也不许越界写。

八个阶段

每阶段的产出是下阶段的唯一输入,任何阶段可单独重跑。

#阶段做什么产出
01发现渠道 adapter 按配置抓取候选;渠道差异只住 adapter,注册表决定启用哪些带来源与抓取时点的原始记录,不做清洗
02规范化把异构渠道字段映射到统一的目标实体;映射在配置里,不在代码里统一实体;校验不过的落入失败表
03身份求稳定键并跨渠道合并同一人,只在有可验证连接证据时合并去重后的目标;无键者落入待裁决池
04富化补受众规模、主题域、可达联系方式;不同字段可来自不同渠道与时点,不强行拉平每字段独立携带来源与观测时点
05分层按配置化规则给出层级与优先级;排序、筛选、报表共用同一份实现层级与优先级
06状态由事件推导每个目标当前所处的阶段派生状态(可从事件重算)
07投影把机算结果写进 Sheet 的机算列;写前比对表头与行锚,对不上即中止Sheet 机算列更新
08对账读回人填列的变化,转成事件喂回状态阶段新事件,回路闭合

状态由事件推导

七条不变量里最反直觉的一条,单独画出来。

设计不变量

违反其中任何一条的改动都是 bug,不是配置疏漏。

  • 人填与机算分区每一列的所有权唯一:要么流水线写,要么人写,绝不双写。越界即中止。
  • 显示名永不作键人会改名换头像,平台原生标识符不会。
  • 状态由事件推导不存在「把状态改成 X」,只有「记录发生了 Y」。状态能从事件重算,反之不行。
  • 每个观测带来源与时点取不到来源的值不是观测,是猜测,不进流水线。
  • 写 Sheet 只进不覆写入前校验表头与行锚,对不上即中止;绝不整表覆盖。
  • 联系人数据不落 repo真人信息只住 Sheet,中间态留在本地不入库。
  • 失败安全宁可少一个目标,不可混入一个错的人。

它修掉了今天的什么

下面四条都是从当前 Sheet 实测出来的,不是假想的问题。

身份靠显示名

现在Name / Handle 事实上充当键,重复行与状态对不上由此而来。
设计键 = 平台 + 平台内原生标识符;求不出键的进待裁决池,永不进主表。

三份状态互不校验

现在Target List、Contact Log、Outcome & Feedback 各维护一份状态列。
设计单一状态机,由事件推导;三张表上的状态列都成为同一状态的投影。

整列默认值刷满

现在表面行数远大于真实行数,行数不能作为任何判断的依据。
设计机算列由流水线独占,真实行由行锚界定,不靠「非空」猜测。

人机互相覆盖

现在没有列所有权约定,谁都可以改任何格。
设计列所有权写进配置;流水线越界写入即中止并报告。

范围之外

点击跟踪、投放结算与付款记录属于谈成之后的下游,不在本流水线内。 外部参考件 build-partnership-tracker 正是做那一段的——它从「已确认合作」开始, 装不下候选到回复这整段漏斗,所以不整包引入。值得移植的是它 manifest → 校验 → 物化 的三段式 与校验严格度。
