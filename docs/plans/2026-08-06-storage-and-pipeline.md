# 存储层与流水线落地

把 skill 从「渠道说明书」变成「跑得动的流水线」。存储按 skill 形态放到用户级目录,
记录形状定死,五阶段接上,然后跑第一批。

## 背景

`src/` 是空的。此前所有验证都是一次性脚本,产出留在 `data/experiments/`。
存储位置的参照物是 last30days 与 auto-gtm:**skill 的 state 是 per-user 的,不是 per-repo 的** ——
换个目录触发就读不到自己的 log,判重当场失效。

## 单元一:设计文档

`docs/design/storage.md` 新建,写三件事:分层判据、记录形状、以及为什么判重库是缓存。
同时改掉 `CLAUDE.md` 里 `data/` 那一行与 `config/` 的描述,`records.md` 里 log 的落点。

**验收:** `data/` 在文档里不再承载流水线状态;三层各自的入场券可以从文档里读出来。

## 单元二:记录与存储

一个记录类型,core + 渠道 payload;一路加字段,末尾一个 outcome。
存储只追加,按渠道分文件,读时求并集。判重键即主键。

**验收:** 同一个 `(人, 渠道)` 写两次只留一条;失败的取数不产生记录;
地址条目与人的条目共用一个库但不共用键。

## 单元三:取数与第二跳

单一入口的礼貌取数器;第二跳从平台页走到本人站点再走到联系页。
原始响应落盘,只有解析器读它。

**验收:** 每主机有间隔;403/429 即停不重试;抓来的文本永不进入任何拼 prompt 的路径。

## 单元四:渠道 adapter

一个渠道一个 adapter,只有它认得自己的 payload。共享的 tail 里不出现任何渠道名。

**验收:** 加一个渠道不改共享代码;去掉一个渠道其余照跑。

## 单元五:闸门

准入两条 —— 有联系方式、符合要求。本轮的「符合要求」是规模带加接单意愿。
规模带只在平台给数字的渠道上生效,不给数字的渠道由接单意愿信号承担。

**验收:** 单位不同的受众数字不会被互相比较;买方不进表只进 log。

## 单元六:Sheet 写入

只追加。写前取当前表头比对,对不上即中止。gid 运行时查,不存。

**验收:** 表头不符时不写任何一行;重复运行不产生重复行。

## 单元七:跑第一批

每渠道十个,YouTube 除外。产出一份运行报告。

**验收:** 报告里每个渠道都有停止原因与产出率;所有进表的行都能追到证据。
