# 计划:把流水线做成 skill,渠道做法进 reference

## 为什么

设计文档已经把**是什么**和**为什么**写完了,缺的是**怎么做**——尤其是每个渠道的联系方式
到底在哪一页、从哪个入口进。这类知识是运维手册,按 CLAUDE.md 的两条豁免归 skill,不归
`docs/design/`。

## 决定

- skill 放**仓库根 `skills/outreach/`**,不是 `.claude/skills/`。代价是 Claude Code 不自动
  发现,本地要另做软链或 marketplace 配置——这一步不在本次范围,记进 TODO。
- reference **一个平台一个 md**,与目标表 `Platform` 列一一对应,外加两个赞助位市场
  (它们不是 `Platform` 值,但是已验证的两条路之一)。
- 共同的第二跳(平台页 → 本人站点 → 联系页)抽成**一个共享件**,各渠道引用不复述。
  这是在「一平台一 md」下保住 DRY 的唯一办法。
- **骨架优先**:页面结构、字段名这类经验断言先写下来并标为未验证,逐条进 `docs/TODO.md`,
  不在本次实测。

## 单元

### 1. 设计文档与索引

先改文档,再碰别的。

- `docs/design/index.md` —— 增加一条权威源划分:渠道做法住 skill 的 reference,
  设计文档不写。
- `CLAUDE.md` 的 Layout —— 回填 `skills/` 一节(该节明写「需要时再建并回填」)。
- `README.md` —— 状态从「只有配置骨架」更新为「skill 已就位,取数与 Sheet 读写未实现」。

**验收**:三份文档互不重复;`docs/design/` 里没有出现任何页面结构、字段名、URL 形态。

### 2. `skills/outreach/SKILL.md`

流水线的操作面:何时用、开工前读什么、运行循环、渠道索引、安全红线。

**验收**:frontmatter 的 description 能让 agent 在「找博主 / 抓联系方式 / 补目标表」这类
请求上命中;不变量与范围**链接**到 `docs/design/`,不复述;渠道索引表覆盖目标表里出现过的
全部平台值。

### 3. `skills/outreach/reference/`

17 个渠道 md + 1 个共享件。每份统一结构:入口 / 拿联系方式 / 停止语义 / 去重的键 /
已知边界 / 待验证。

**验收**:每份都能独立回答「这个平台的联系方式从哪进、怎么拿、什么时候停」;
第二跳只在共享件里写一次;**没有任何一份含真实姓名、邮箱或 handle**。

### 4. 验证

无代码,故无单测——测试规则针对代码,markdown 骨架不适用,这一点明说而不是默默跳过。

实际要做的三件事:

- 全部 md 内部链接可解析,无死链。
- 全库扫一遍,确认没有真实联系人数据混进 `skills/`。
- 各 md 的「待验证」条目**逐条**出现在 `docs/TODO.md`,不漏。

**验收**:三件事都有命令跑过的输出,不是目测。

### 5. 提交与清扫

绿点提交并 push。清扫 `docs/design/index.md`、`README.md`、`docs/TODO.md`。

## 不在本次范围

取数层实现、Sheet 读写、log 落地、种子词表——它们在 `docs/TODO.md` 里各自排队,
本次只提供它们将来要遵循的渠道说明。
