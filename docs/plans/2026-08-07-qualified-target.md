# 每渠道凑够合格数,按档位限定范围

## 为什么

设计早已写明:**使用者给的那个数是最终合格的行数,不是爬多少个**
(见 [platforms.md](../design/platforms.md) 与 [index.md](../design/index.md))。
实现读成了「判定多少个」——上一轮每渠道判了 10 个就停,合格 3 条。
这是代码偏离文档,不是设计要改。

第二件:**档位现在只住在 methodology 的目录名里,流水线读不到**,
因此「只跑前两档」无法表达。

## 单元一 —— 文档钉住停止语义与档位范围

- `docs/design/platforms.md`:停止三种里的「凑够」明确以**合格数**计;
  补第四种——池子取干仍没凑够,与「连续无新」是同一件事的两种成因,报告要能分。
- `docs/design/platforms.md`:**档位是运行时的选择维度**,不是新的配置事实 ——
  渠道属于哪一档的权威源仍是 methodology 的目录,配置里只存**指向那份文档的路径**,
  档位由路径推出。移动文件会强制更新指针,复制一份档位号则会悄悄漂。

验收:两份文档读完能回答「10 是什么的 10」与「档位从哪来」,且没有第二处写档位号。

## 单元二 —— 测试

`tests/test_run.py`(新建),全部用假 adapter 与假 store,不碰网络:

- 目标数以**合格**计:池子里前 N 个不合格、后面才有合格的,要一直判到凑够。
- 池子取干仍不够:停止原因是「连续无新」(搜索型)或「翻到底」(目录型),不是「凑够」。
- 判重:已在 store 里的候选不消耗目标数。
- 档位过滤:只跑指定档位的渠道,其余一个请求都不发。
- 指针完整性:配置里每个渠道的 methodology 路径在仓库里真实存在。

验收:先红后绿。

## 单元三 —— 代码

- `run.py` 的渠道循环改为「判到合格数够或池子干」,池子按目标数的倍数取。
- `config/channels.toml` 每个渠道加 methodology 指针。
- CLI 加档位选择;报告里「计划」一列的语义随之改为合格目标数,
  并删掉写死在渲染里的上一轮意图。

验收:单测全绿。

## 单元四 —— 端到端

对前两档实跑一轮,产出运行报告。写 Sheet 仍卡在 token scope,
本单元只到 stage 为止,不动正式表。

验收:报告里每个渠道都有明确的停止原因;凑不够的渠道说得出是池子干了还是闸门卡住。
